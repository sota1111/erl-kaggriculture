# 課題:Kaggriculture のエージェントを作る(構造探索アーム)

Kaggle の `kaggriculture`(2人対戦の農業経営シミュレーション)で対戦するエージェントを、
**白紙から**実装せよ。公開されている他人の解法は渡されていないし、取りに行ってもいけない。

## 最初に読むもの(この順)

1. `docs/competition_brief.md` — このコンペの正本。スコアの正体と制約
2. `docs/env/GETTING_STARTED.md` — observation / action の全仕様
3. `docs/env/RULES.md` — 公式ルール。作物表・価格関数・町の需要・ターン処理順
4. `AGENTS.md` — 守るべき契約

## 作るもの

このディレクトリ直下に置くこと。

```
main.py                  # agent(obs) を export する。これが提出物本体
agent_submission.json    # 下表の必須キー
```

`agent_submission.json`:

| キー | 内容 |
| --- | --- |
| `approach_summary` | 戦略の族(固定ポリシー / ルールベース制御 / 探索 / 学習ベース / 混合)、経済の回し方、労働力配分、土地解放の判断、依拠した経済的洞察 |
| `local_eval` | `tools/eval_local.py` の出力(所持金と破綻チェック) |
| `failure_modes` | 例外・タイムアウト・no-op で落ちた条件と、どう潰したか |
| `timing` | 1ターンの最悪実行時間(制限 1 秒)と 720 ターンの累計 |
| `rejected_hypotheses` | 試して捨てた方針と理由 |

## 使える道具

**Python は必ず `.venv/bin/python` を使うこと**(`kagsim` と `kaggle_environments` が入っている)。

```bash
.venv/bin/python tools/validate_submission.py main.py   # 提出契約の機械チェック
.venv/bin/python tools/eval_local.py main.py            # 組み込み相手と自己対戦での採点
bash tools/build_submission.sh .                        # submission.tar.gz を作る(提出はしない)
```

`tools/engine.py` が bit-exact な C++ エンジン `kagsim` を使う(1エピソード約 0.4 秒)。
**ローカル試行は安い。多く回すこと。**

## 知っておくべきこと

- **`tools/eval_local.py` が使える相手は弱い。**組み込み `starter` に勝つことは
  破綻していないことの確認にしかならない。**実力の識別はできない。**
  本当の採点は Controller が非公開の相手フィールドに対して行う。
- **相手と市場を共有する。**両者が売れば価格は崩れる。空いた市場を独占する戦略は、
  相手が強いときに機能しない。**自己対戦で確認すること。**
- **回復不能な状態がある。**2日連続の水やり忘れで雑草化、2日連続の給餌忘れで家畜逃亡。
  起きてからでは戻せない。
- **市場注文は1ターン10件まで。**超過分は黙って捨てられるので順序が意味を持つ。
- **例外を投げない。**全体を try/except で包み、最悪でも
  `{"farmer": ["PASS"], "hands": [], "market": []}` を返すこと。
- **両席(player 0 と 1)、複数 seed で確認すること。**評価の seed は渡されない。

## 終了条件

- `.venv/bin/python tools/validate_submission.py main.py` が PASS
- 12 seed × 両席で例外・タイムアウトを出さず完走する
- `agent_submission.json` の必須キーが埋まっている

## 構造を自分で確かめること(このアームの追加要求)

ルール文書は仕様を述べるが、**何が儲かるかは述べていない。**そこは自分で測れ。
以下は「調べよ」という指示であって、答えではない。**測っていない主張を
`approach_summary` に書いてはならない。**

- **市場の価格関数。**販売価格は市場在庫に対してどう動くか。商品ごとに形状が違い、
  共有初期在庫を境に上下で別の関数になる。**どの商品が供給過剰で床まで崩れ、
  どの商品が耐えるか**を、実際に売って測れ。
- **1.32.7 のリバランス。**carrot / tomato / egg に凸型の希少性ブランチが入っている。
  **通常のエピソードでその変曲点を越えるのはどの商品か。**越えたとき価格はどうなるか。
- **町の需要。**町の中心と、3日ごとに解放される店(重複あり)が何をいくつ消費するか。
  **需要は時間とともにどう増えるか。**それは何を作るべきかをどう変えるか。
- **労働力の限界収益。**雇用コストは日次リセットの `fib(n)`。**何人目で赤字になるか。**
  それは日によって、また農場の広さによって変わるか。
- **土地解放の投資回収。**NE $1,000 / SW $2,000 / SE $4,000 は、シーズンの何日目までに
  買えば元が取れるか。買わない方が良い局面はあるか。
- **相手との結合。**農場は独立だが市場は共有である。**自己対戦で、相手が同じものを
  売るときに自分の収入がどれだけ落ちるかを測れ。**空いた市場を独占する戦略は、
  そこで機能しなくなるはずである。
- **回復不能状態のコスト。**雑草化・家畜逃亡が起きたとき、シーズン全体で何を失うか。

`agent_submission.json` の `approach_summary` には、**測った結果として何が分かり、
それが設計をどう決めたか**を書くこと。`rejected_hypotheses` には、測って否定された
仮説を書くこと。
